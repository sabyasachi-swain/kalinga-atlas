### A1. The route/port count disagrees with what's on screen

**As a visitor**, when I read "Mauryan Kalinga · 6 routes, 11 places" under
the map, **I want the number to match what I can actually see**, so that I
don't think the map is broken or empty.

**Context.** `AtlasMap.tsx`'s `.atlas-map__count` label counts every active
marker/route for the period, including ones in Sri Lanka, Myanmar and Sumatra
that sit far outside the default coast-view crop. The opening-view fit was
already widened once (see `HANDOFF.md`, "Phase 1... §1.4/§1.5") to include
more of the Odisha coast, but distant destinations are still off-screen by
design — pulling them into the default view would make the Odisha coast tiny.
The result: the label says "11 places" while a visitor looking at the coast
view can count 3–4. This is the root cause behind an owner report: *"at first
I thought it only has 2 results... I got confused."*

**Acceptance criteria:**
- The visible count reflects what's drawn **inside the current view's visible
  bounds**, not the full active set — e.g. "6 routes · 4 places in view (11
  total)" or similar, worded for a 10-year-old.
- Switching to "Show the whole ocean" updates the count to match that view.
- Do not just widen the coast fit further to cram everyone in — that was
  tried and makes the Odisha coast (the actual subject of the atlas)
  unreadably small. Solve the *label*, not the geometry, unless you find a
  fit that keeps Odisha legible AND gets everyone on screen, in which case
  either is fine.
- 0 pin/label overlaps at 1280×900 and 380×800 (use the probes described
  below — do not skip this because the change looks small).

**Files:** `src/islands/AtlasMap.tsx` (search `atlas-map__count`, `coastFitPoints`,
`oceanFitPoints`).

**Verify against `dist/`, not the dev server.** Probes exist in past

### B1. "Sail this route" — animate a ship along the selected route with sourced stopping points

**As a child using the atlas**, when I select a route, **I want a button that
sails a little ship along it**, pausing at each real stop to tell me one true
thing that happened there, so the route feels like a story instead of a line
on a map.

**Context.** This is the single highest-value feature per the original
improvement plan (`docs/design/improvement-plan-2026-09-16.md`, Phase 3.1).
**Important constraint discovered since that plan was written:** route
waypoints are largely unsourced geometry, not real named stops — see
`HANDOFF.md`, section "The route-stops finding". After that finding, every
route's detail panel lists only its two sourced endpoints (`from`/`to`) plus
an "approximate course" note; no route currently has a named intermediate
stop, because none could be honestly sourced. **This means "Sail this route"
today can only pause meaningfully at a route's two endpoints**, unless Epic F
below produces sourced intermediate stops first. Do not invent stops to make
the animation more interesting — that is exactly the mistake `HANDOFF.md`
documents being caught and reverted.

**Acceptance criteria:**
- A "Sail this route" button appears in the route detail panel
  (`src/islands/DetailPanel.tsx`) when a route is selected.
- Clicking it animates a ship (reuse the existing ship glyph/animation
  machinery already in `AtlasMap.tsx` — search `SHIP_FOR_MODE`, `shipRef`,
  the `place()` closure — do not build a second animation system) along the
  route's drawn path.
- The ship pauses at the route's sourced stops only (today: just the two
  endpoints; more if Epic F has landed by the time this is built) and shows
  one short, sourced sentence per stop, pulled from that entity's own data
  (`kid_line` field on the port/site, or the route's own `kid_line` — check
  `src/data/schema.ts` for what's available). **Every sentence shown must
  trace to a `source_refs` entry, same rule as every narrative on this site.**
- `prefers-reduced-motion`: either skip straight to showing the stops as a
  static list, or play the animation without motion — do not force motion
  on a visitor who's asked not to see it.
- Keyboard-operable: the button is reachable and activatable without a
  mouse; the stop text is announced to screen readers as it changes
  (`aria-live`), not conveyed only by animation.
- 0 new console errors; `npm run check` / `npm run build` clean.

**Files:** `src/islands/AtlasMap.tsx` (ship animation), `src/islands/DetailPanel.tsx`
(button placement), `src/lib/route-stops.ts` (existing stop-classification
logic from Phase 1 — reuse `getRouteStops`/`classifyWaypoints`, don't
reimplement).

**As a child who doesn't know where to start**, I want a friendly guide
character who nudges me toward things to try, without ever telling me a
historical fact herself (facts always come from a sourced entity, never from

**Context.** Asset: `guide-disha.svg`, plus `compass-hint.svg`. The existing
first-load hint system (`HINT_KEY`/`hintVisible` in `AtlasMap.tsx`, "Tap a

**Acceptance criteria:**
- Disha's suggestions are all **instructions to interact** ("Try dragging

- Appears at sensible moments (first load, or when a visitor seems stuck —
  design your own trigger, but don't spam it) and is dismissible, remembered
  via `localStorage` like the existing hints.
- Keyboard-reachable, `prefers-reduced-motion` honoured if animated.
- Does not duplicate or fight the existing `HINT_KEY` marker-hint — either
  replace it with Disha, or make clear how the two coexist. Ambiguity here
  will produce two competing nudges on screen at once; that's the failure

**Files:** likely a new component under `src/islands/` (if it needs
